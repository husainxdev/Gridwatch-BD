## Findings and fixes

| Finding | Change and evidence |
| --- | --- |
| Revised previously published evidence could become deletable as a draft | Publication audit blocks hard deletion; cancel/archive keeps evidence. Backend regression test covers this path. |
| Location/report/event actions lacked consistent stale-edit protection | Persisted versions, row/advisory locking, 409 on stale writes, transactional before/after audit. Concurrent schedule test has one winner and one rejection. |
| History summary and page could see different committed versions during moderation | REPEATABLE READ snapshot. A test inserts a concurrent episode between calculation and page read; the first response remains internally consistent and the next sees the new record. |
| Repeated restoration confirmations could inflate episode counts or move the recorded end | Consecutive back reports remain on one episode and preserve first restoration; moderation rebuild follows the same rule. Original observations remain intact. |
| Clock-skew-tolerated future reports could close an episode before the observed time | Retain as pending. Early acceptance is rejected; later explicit review can include the original timestamp. No clock-based automatic restoration. |
| Exact session/reset expiry boundary was accepted | Expiry comparisons now reject `expires_at <= now`; controlled-clock tests cover access session, refresh and reset. |
| Malformed stored password hashes could raise an internal error | Verification treats invalid hashes as invalid credentials; regression test returns 401. Password/reset input sizes are also bounded. |
| Whitespace-only review reasons and normalized-overlength names | Strip/revalidate reasons; check NFKC-expanded lengths before writing PostgreSQL. Tests expect 422 rather than an internal database error. |

| Office panel originally exposed only publisher metadata | Added separate persisted, sourced office/feeder-claim registry with Admin-only CRUD, review/invalidation, versions, audit and reference-safe deactivation. It does not manufacture real records or silently infer schedule coverage. |

| User requested Next.js frontend | Replaced Vite and React Router with explicit Next.js App Router pages, Next navigation and a same-origin API rewrite. Browser tests run against a real Next production build; PostgreSQL/FastAPI persist the same data. |
| Independent tabs could race refresh rotation or retain a previous account’s private view | Coordinate cookie changes with Web Locks and memory-only BroadcastChannel; remount private views on account changes. ## Remaining boundaries and external prerequisites

1. **Current technology:** Next.js App Router + React + TypeScript (compiled to JavaScript), Tailwind/DaisyUI, FastAPI and PostgreSQL. The user clarified Next.js frontend, so FastAPI is preserved. See [Next.js migration](NEXTJS.md) for routing, deployment and validation details.
2. **Real pilot evidence:** a real Sylhet boundary/provider and official notices/feeder claims still need source verification. Registry functionality is real, but operational facts are not fabricated to fill it. Test fixtures are fictional and isolated.
3. **Feeder schedule linkage:** reviewed registry claims remain separate from announcements. Automatic feeder-to-schedule propagation and official API ingestion are not implemented. Named administrative coverage must come explicitly from a notice; a boundary does not prove electrical coverage.
4. **Deployment/email:** hosting/domain configuration, real SMTP delivery, public-domain cookies, ingress controls/backups and live verification remain external deployment work. Development Mailpit does not establish external delivery.
5. **Auth topology:** deployment supports the documented same-origin frontend/API arrangement. The authentication rate limiter is per process; multiple instances need shared ingress limits. Strict refresh replay protection remains. Web Locks serialize cookie-changing operations across tabs; BroadcastChannel shares fresh credentials only in memory. A new tab validates peer credentials with the backend, account changes remount private views, and confirmed logout clears other tabs. Modern browsers on HTTPS/localhost support this coordination. Where Web Locks or BroadcastChannel are unavailable, in-tab single-flight still works but competing tabs may require re-login; cross-device coordination is not claimed.
6. **History:** self-reports are incomplete evidence, not area reliability or SAIDI/SAIFI. Unknown/open time stays unknown. Old stored groupings are preserved by migration and can be rebuilt through reviewed moderation; no silent historical rewrite is performed. Large history selections are explicitly capped rather than silently truncated. Large-scale moderation/load performance has not been certified.
7. **Future phases:** Sections 11–14's dedicated comprehensive review, hosted release and final submission remain separate work. The checks above are the actual verification completed for this implementation.

## Update an existing Windows checkout

Keep existing `.env` credentials and the working PostgreSQL host port (including 15432 if used). In PowerShell, after pulling the committed changes:

```powershell
cd "$env:USERPROFILE\Gridwatch-BD\backend"
py -m uv sync --frozen --python 3.12
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

In a second terminal:

```powershell
cd "$env:USERPROFILE\Gridwatch-BD"
npm.cmd ci --prefix frontend
npm.cmd run dev --prefix frontend
```

Do not close either server terminal while using `http://localhost:5173`. Migration alone does not run the website. See [Sections 9–10](SECTIONS-9-10.md) for manual API/UI verification.
